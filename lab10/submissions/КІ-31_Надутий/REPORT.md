### Питання для звіту 1

**Скільки рядків у defconfig і .config? Чому в Git потрібно
зберігати саме defconfig?**

У стандартному qemu_x86_64_defconfig є 18 рядків,
а в розгорнутому .config — 5307 рядків.

defconfig містить лише параметри, які відрізняються
від значень за замовчуванням. Тому він компактніший,
зручніший для перевірки змін і відтворення конфігурації.
Повний .config генерується автоматично інструментами
Kconfig і не потрібний у Git як основне джерело налаштувань.

**Яка версія GCC у тулчейні і що повертає -print-sysroot?**

Компілятор цільової системи:
x86_64-buildroot-linux-gnu-gcc, версія GCC 15.3.0.

Команда -print-sysroot повернула:
`/home/denna/br-stock/host/x86_64-buildroot-linux-gnu/sysroot`.

Sysroot — каталог із заголовками й бібліотеками цільової
системи, які компілятор використовує під час крос-компіляції.

**Чому в staging/usr/include є заголовки, а в target/ їх немає?**

staging (sysroot) містить файли для збирання програм:
заголовки, бібліотеки та метадані розробки.

target містить файли, необхідні для виконання програм
на готовому пристрої. Заголовки C для запуску програм
не потрібні, тому їх туди зазвичай не встановлюють.

**Чим є /bin/ls у гостьовій системі й чому?**

Перевірка показала, що `target/bin/ls` — символічне
посилання на `busybox`.

BusyBox об'єднує багато стандартних команд Linux
в одному виконуваному файлі. Це дозволяє скоротити
розмір вбудованої системи.

Різниця становить 27m24.235s, тобто власна збірка

У стандартній збірці виявлено 54 каталоги host-*,

Bootlin і системний QEMU, тому не потребує
збирання цих компонентів із вихідного коду.

**Чому не можна змінити тулчейн у вже зібраному каталозі?**

Компілятор, бібліотека C, ABI, sysroot та інші
компоненти тулчейна мають бути узгодженими.

Buildroot використовує файли .stamp_* для фіксації
виконаних етапів. Після зміни тулчейна він не
гарантує автоматичного перезбирання всіх пакетів,
зібраних старим компілятором.

Тому для надійного переходу на інший тулчейн
потрібно виконати make clean all або створити
новий каталог збирання.

**Навіщо вимикати CONFIG_LOCALVERSION_AUTO?**

Ця опція може дописувати до версії ядра інформацію
про стан вихідного Git-дерева, зокрема суфікс «+»
або ідентифікатор коміту.

Її вимкнення дозволяє отримати передбачувану
версію 6.18.7-lab10. Це важливо для сумісності
зібраних модулів ядра.

**Чому фрагмент кращий за копію всієї конфігурації?**

Фрагмент зберігає тільки потрібні зміни й не
дублює сотні або тисячі параметрів базової
конфігурації плати.

Після переходу на нове ядро фрагмент можна
повторно накласти на нову базову конфігурацію.
Проте змінені або видалені опції необхідно
перевірити, оскільки вони можуть бути проігноровані
чи отримати інші значення.

Повна скопійована конфігурація сильніше прив'язана
до конкретного випуску ядра й ускладнює супровід.
