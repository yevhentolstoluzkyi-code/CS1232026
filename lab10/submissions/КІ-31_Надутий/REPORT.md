### Питання для звіту 1

**Скільки рядків у defconfig і .config? Чому в Git потрібно
зберігати саме defconfig?**

У стандартному qemu_x86_64_defconfig є 18 рядків,
а в розгорнутому .config — 5307 рядків.

defconfig містить лише параметри, які відрізняються
від значень за замовчуванням. Тому він компактніший,
зручніший для перевірки змін і відтворення конфігурації.
Повний .config генерується автоматично інструментами
Kconfig і не потрібний у Git як основне джерело налаштувань.

**Яка версія GCC у тулчейні і що повертає -print-sysroot?**

Компілятор цільової системи:
x86_64-buildroot-linux-gnu-gcc, версія GCC 15.3.0.

Команда -print-sysroot повернула:
`/home/denna/br-stock/host/x86_64-buildroot-linux-gnu/sysroot`.

Sysroot — каталог із заголовками й бібліотеками цільової
системи, які компілятор використовує під час крос-компіляції.

**Чому в staging/usr/include є заголовки, а в target/ їх немає?**

staging (sysroot) містить файли для збирання програм:
заголовки, бібліотеки та метадані розробки.

target містить файли, необхідні для виконання програм
на готовому пристрої. Заголовки C для запуску програм
не потрібні, тому їх туди зазвичай не встановлюють.

**Чим є /bin/ls у гостьовій системі й чому?**

Перевірка показала, що `target/bin/ls` — символічне
посилання на `busybox`.

BusyBox об'єднує багато стандартних команд Linux
в одному виконуваному файлі. Це дозволяє скоротити
розмір вбудованої системи.

**Чому не можна змінити тулчейн у вже зібраному каталозі?**

Компілятор, бібліотека C, ABI, sysroot та інші
компоненти тулчейна мають бути узгодженими.

Buildroot використовує файли .stamp_* для фіксації
виконаних етапів. Після зміни тулчейна він не
гарантує автоматичного перезбирання всіх пакетів,
зібраних старим компілятором.

Тому для надійного переходу на інший тулчейн
потрібно виконати make clean all або створити
новий каталог збирання.

**Навіщо вимикати CONFIG_LOCALVERSION_AUTO?**

Ця опція може дописувати до версії ядра інформацію

Її вимкнення дозволяє отримати передбачувану

зібраних модулів ядра.

**Чому фрагмент кращий за копію всієї конфігурації?**

Фрагмент зберігає тільки потрібні зміни й не
дублює сотні або тисячі параметрів базової
конфігурації плати.

Після переходу на нове ядро фрагмент можна
повторно накласти на нову базову конфігурацію.
Проте змінені або видалені опції необхідно
перевірити, оскільки вони можуть бути проігноровані
чи отримати інші значення.

Повна скопійована конфігурація сильніше прив'язана
до конкретного випуску ядра й ускладнює супровід.

### Питання для звіту 5

**Що показує `readelf -p .comment` для програми з `target/`
і для програми, зібраної на хості? Чому вони різні?
Які версії libc використовуються? Що станеться,
якщо скопіювати хостовий бінарник в overlay?**

На хості програма скомпільована GCC 11.4.0 (Ubuntu),
а в Buildroot — GCC 14.3.0 із зовнішнього тулчейна
Bootlin. Це підтверджено секцією `.comment`.

Спочатку Buildroot видаляв секцію `.comment` під час
strip. Щоб тест міг перевірити компілятор, у defconfig
додано `BR2_STRIP_EXCLUDE_FILES="lab10-sysinfo"`.
Після повторного встановлення програми `readelf`
показав GCC 14.3.0 (Buildroot).

На хості WSL2 `lab10-sysinfo` повідомила glibc 2.35,
у гостьовій системі QEMU — glibc 2.41.

Копіювання хостового виконуваного файлу в overlay
не гарантує працездатності: він може залежати від
іншої версії glibc, завантажувача ELF, бібліотек
та ABI. Навіть за однакової архітектури x86-64
таке копіювання обходить правильну крос-компіляцію.

### Питання для звіту 6

**Чому після зміни `lab10-sysinfo.c` просте `make`
може не перезібрати пакет? Що роблять
`lab10-sysinfo-rebuild` та `all`?**

Пакет використовує `SITE_METHOD = local`.
Buildroot копіює джерела у власний каталог
`build/lab10-sysinfo-1.0` і фіксує етапи збирання
штампами `.stamp_*`. Зміни локальних вихідних файлів
не завжди автоматично скасовують ці штампи.

Ціль `lab10-sysinfo-rebuild` повторно синхронізує
джерела, збирає та встановлює пакет.
Ціль `all` продовжує загальне збирання, зокрема
генерує файлову систему й кінцевий образ.

Без `all` пакет можна оновити в `target/`,
але готовий `rootfs.ext2` може залишитися старим.

### Питання для звіту 7

**Який `vermagic` модуля, з чого він складається?
Що буде за іншого `vermagic`? Чому каталог `updates/`?**

Команда `modinfo` показала:
`6.18.7-lab10 SMP preempt mod_unload`.

Тут `6.18.7-lab10` — випуск ядра з нашим суфіксом,
`SMP` — підтримка багатопроцесорності,
`preempt` — параметри витіснення ядра,
`mod_unload` — підтримка вивантаження модулів.

За несумісного `vermagic` ядро зазвичай відхилить
завантаження модуля з помилкою формату модуля
(`Invalid module format`), оскільки внутрішній
бінарний інтерфейс модулів Linux не є стабільним.

Модуль встановлено в
`/lib/modules/6.18.7-lab10/updates/`, тому що
це зовнішній модуль, який збирається окремо від
джерел ядра через інфраструктуру `kernel-module`.

### Питання для звіту 8

**Що буде після зміни `CONFIG_LOCALVERSION`
і `make linux-rebuild all`? Що треба виконати?**

Зміна `CONFIG_LOCALVERSION` змінює ідентифікатор
випуску ядра, а з ним каталог модулів та `vermagic`.

Самого `make linux-rebuild all` недостатньо,
щоб гарантувати перебудову зовнішнього модуля.
Старий модуль може залишитися у каталозі
попереднього випуску або виявитися несумісним.

Потрібно перебудувати ядро та залежний модуль,
зокрема виконати `make lab10-hello-rebuild all`
після оновлення ядра. За суттєвих змін конфігурації
може знадобитися повне очищення та збирання.

Це демонструє, що Buildroot використовує штампи
етапів і не відстежує всі зміни транзитивних
залежностей автоматично.

### Питання для звіту 9

**Що відповідає SSH після перезбирання образу?
Звідки береться ключ хоста, чому він змінюється
і як правильно обробляти його зміну?**

Під час першого успішного SSH-з'єднання клієнт
повідомив, що ED25519-ключ хоста додано до
`known_hosts`. Підключення через порт 10022
працювало за користувацьким ключем Ed25519.

Dropbear створює ключі хоста на гостьовій системі
під час її першого запуску. Якщо ці ключі не
включені до постійного образу, новий rootfs
може отримати інший ключ хоста.

За повторного підключення до тієї самої адреси
з іншим ключем SSH може попередити
`REMOTE HOST IDENTIFICATION HAS CHANGED`.
Цей конкретний текст попередження під час
експерименту ще не зафіксовано.

Однаковий приватний ключ хоста на всіх пристроях
партії небезпечний: компрометація одного пристрою
дозволить видавати себе за інші. Постійне
вимкнення перевірки ключів створює ризик
атаки посередника (MITM).

Після перевірки справжності нового ключа
старий запис можна прибрати командою:
`ssh-keygen -R '[127.0.0.1]:10022'`.
Після цього потрібно перевірити та прийняти
новий відбиток ключа, а не сліпо довіряти йому.
