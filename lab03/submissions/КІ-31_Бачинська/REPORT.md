# ЛР 3. Бачинська, КІ-31
Середовище: Windows 11, WSL 2, Ubuntu 22.04, GCC, Make 4.3, Git 2.34.1, Rust / rustc, Cargo, Valgrind 3.18.1

Таблиця вимірювань:
| Показник                      | C       | Rust    |
| Рядків коду (wc -l)           | 36      | 41      |
| Час першої збірки             | 0,123 с | 0,274 с |
| Час повторної збірки без змін | 0,003 с | 0,018 с |
| Розмір бінарника, debug       | 19 КБ   | 4,6 МБ  |
| Розмір бінарника, release     | 19 КБ   | 462 КБ  |

Питання для звіту:
1. Команда `cat .git/HEAD` показує, на яку гілку зараз вказує HEAD. У моєму випадку це гілка `lab03-bachynska`. Команда `cat .git/refs/heads/lab03-bachynska` показує хеш коміту, на який вказує ця гілка. Це демонструє, що гілка в Git є вказівником на певний коміт.
2. Якщо прибрати `free(line)`, пам’ять, яку виділяє `getline`, після завершення роботи з нею не буде звільнена. Valgrind показує інформацію про використання та витоки пам’яті. У результаті видно, що пам’ять була виділена під час роботи програми і не була звільнена. Після перевірки `free(line)` було повернуто в програму.
3. Другий виклик `make` нічого не робить, тому що вихідний файл не змінився після попередньої збірки. Після `touch minigrep.c` час модифікації файлу змінився, тому `make` виконав збірку знову. `make` порівнює час модифікації залежностей і результатів збірки та отримує цю інформацію з файлової системи.
4. Компілятор Rust повідомив про помилку `E0106: missing lifetime specifier` у функції `fn bad() -> &String`. Функція намагалася повернути посилання на локальну змінну `s`, яка існує тільки всередині цієї функції. Після завершення функції ця змінна більше не існує, тому таке посилання було б некоректним. Rust не дозволив скомпілювати програму. Код із помилкою перед здачею було прибрано.
5. Debug-бінарник Rust значно більший за C-версію через додаткову інформацію для відлагодження та особливості структури Rust-програми. У release різниця значно менша: C — 19 КБ, Rust — 462 КБ, але Rust-бінарник все одно більший.
6. Коміт злиття має два батьківські коміти. Звичайний коміт має одного батька, а merge-коміт об’єднує історію двох гілок. Git не зміг автоматично вирішити конфлікт, тому що обидві гілки змінили один і той самий фрагмент файлу по-різному. Обидва варіанти були синтаксично правильними, але Git не може визначити, який зміст був задуманий користувачем.
7. Під час ручного пошуку Git поступово звужував діапазон комітів і перевіряв середні коміти. В автоматичному режимі `git bisect run ./test.sh` виконував перевірку самостійно. Знайдений зламаний коміт: `77e2d50ac274174e961638b47970c0a813e718b7`
Повідомлення коміту: `оптимізовано цикл підсумовування`.
Проблема була пов’язана зі зміною рядка коду в `sum.c`, яка порушила правильну роботу програми.
8. Якщо один коміт містить тиждень роботи над п’ятьма різними задачами, після знаходження цього коміту через `bisect` буде складніше визначити, яка саме зміна спричинила помилку. Тому коміти варто робити атомарними: один коміт — одна логічна зміна.

Контрольні питання:
1. `getline` самостійно виділяє та за потреби збільшує буфер, тому не потрібно заздалегідь задавати максимальний розмір рядка. Це зменшує ризик переповнення буфера та помилок через занадто малий фіксований масив.
2. У C-версії з `getline` рядок у мільйон символів може бути прочитаний, оскільки буфер автоматично збільшується. При використанні `char buf[256]` через `fgets` весь рядок не поміститься в буфер і його довелося б читати частинами.
3. У Rust пам’ять, зайнята вмістом файлу, автоматично звільняється після того, як відповідне значення перестає використовуватися. За звільнення пам’яті відповідає система володіння Rust та автоматичний механізм `Drop`.
4. Rust не захищає від логічних помилок програми, наприклад неправильного алгоритму або неправильного результату обчислень. Перевіряльник запозичень контролює правила володіння та посилань, але не визначає, чи правильну логіку реалізував програміст.
5. `cargo build` використовує результати попередньої збірки та не перебудовує незмінені частини проєкту. Це схоже на `make`, який також перевіряє, що потрібно перебудувати. Відмінність у тому, що Cargo працює зі структурою Rust-проєкту та його залежностями.
6. Якщо час модифікації файлів збережено неправильно або він змінений таким чином, що не відповідає фактичному вмісту файлу, `make` може вирішити, що перебудова не потрібна, хоча файл фактично змінився.
7. `git merge` об’єднує історію двох гілок і створює merge-коміт, якщо це необхідно. `git rebase` переносить коміти однієї гілки поверх іншої та переписує історію. Переписувати опубліковану історію небезпечно, тому що хеші комітів змінюються і це може створити проблеми для інших користувачів цієї гілки.
8. Гілка в Git є вказівником на коміт, тому для її створення не потрібно копіювати весь проєкт. Створюється лише новий вказівник на існуючий коміт.
9. `git bisect run` визначає результат перевірки за кодом завершення програми або скрипта. Код `0` означає успішну перевірку, а ненульовий код — помилку. Текстовий вивід програми Git не може надійно використовувати як ознаку успіху або помилки.
10. Якщо пароль потрапив у коміт, він залишається в історії Git навіть після видалення наступним комітом. Тому такий пароль потрібно вважати скомпрометованим і замінити його.
11. Конфлікт-вільне злиття не гарантує логічної правильності результату. Наприклад, два студенти можуть змінити різні рядки, але ці зміни можуть суперечити одна одній за змістом. Git побачить різні рядки й автоматично об’єднає їх, хоча отримана програма може працювати неправильно.
12. Якщо `malloc` не перевіряти на `NULL`, а пам’ять закінчилася, програма може отримати нульовий вказівник і спробувати звернутися до недійсної адреси. Це може призвести до помилки доступу до пам’яті та аварійного завершення програми.
Висновки: У роботі було реалізовано одну утиліту `minigrep` двома мовами — C і Rust. Для C було використано `gcc` і `make`, а для Rust — `cargo`. Було перевірено роботу програм, виконано тестування та порівняно час збірки й розміри бінарних файлів. Також було виконано роботу з гілками Git, вручну розв’язано конфлікт злиття та знайдено зламаний коміт за допомогою `git bisect`. У результаті було отримано практичний досвід роботи з C, Rust і Git та підготовлено зміни для подальшого проходження code review через pull request.
