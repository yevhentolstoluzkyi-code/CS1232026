## 3. Відповіді на питання для звіту

### Питання 1
Файл `.git/HEAD` містить символічне посилання `ref: refs/heads/lab03-petrunyshyn`, а файл `.git/refs/heads/lab03-petrunyshyn` — 40-символьний хеш поточного коміту гілки. Це підтверджує, що гілка в Git — легкий вказівник на конкретний коміт[cite: 10].

### Питання 2
Без виклику `free(line)` `valgrind` зафіксував витік у купі: `definitely lost: 120 bytes in 1 blocks` (`total heap usage: 4 allocs, 3 frees, 5,712 bytes allocated`), оскільки буфер, виділений `getline`, не було звільнено до завершення програми. Після повернення `free(line)` витоки зникли (`0 bytes in 0 blocks`, `4 allocs, 4 frees`).

### Питання 3
Другий виклик `make` вивів `Nothing to be done for 'all'`, бо цільовий файл `minigrep` уже існував і мав новіший час модифікації (`mtime`), ніж `minigrep.c`. Після `touch minigrep.c` час модифікації вихідного файлу оновився, тож `make` знову запустив компіляцію. `make` порівнює мітки часу модифікації цілей і залежностей через метадані файлової системи (`stat`).

### Питання 4
Компілятор Rust видав помилку `error[E0106]: missing lifetime specifier` (`expected named lifetime parameter`), оскільки локальна змінна `s` знищується при виході з функції `bad()`, і повернення посилання `&s` призвело б до висячого посилання (dangling reference / use-after-free).

### Питання 5
Debug-збірка Rust значно більша за C-версію (4.6M проти 16K) через вбудовану відлагоджувальну інформацію, допоміжні перевірки та стандартні рантайм-компоненти. У release-збірці розміри суттєво зменшуються (451K для Rust проти 17K для C), але Rust усе одно більший за рахунок статично скомпільованого коду стандартної бібліотеки та оптимізацій.

### Питання 6
На графі `git log --oneline --graph --all` коміт злиття `946fccd` має двох батьків (`fe02345` та `3d6ee8f`), на відміну від звичайного коміту з одним батьком[cite: 1]. Git не вирішив конфлікт самостійно, бо обидві гілки змінили той самий рядок у `REPORT.md` по-різному, і вибір коректного змісту вимагає рішення людини[cite: 1].

### Питання 7
Пошук виконано за 5 кроків (що відповідає оцінці $\log_2 30 \approx 4.91$) як вручну, так і через `git bisect run ./test.sh`[cite: 2, 3, 4]. Зламаний коміт: `24ab81e88892275b412a84f7026b8870467f9786` («оптимізовано цикл підсумовування», зміна у файлі `sum.c`)[cite: 2, 3, 4].

### Питання 8
Якщо один коміт містить тиждень роботи над п'ятьма різними задачами, `git bisect` вкаже на великий «змішаний» коміт, і доведеться вручну розбиратися, яка саме частина змін внесла дефект. Атомарні коміти роблять кожен крок історії цілеспрямованим і спрощують локалізацію та відкат помилок.

## 4. Контрольні питання
1. `getline` динамічно виділяє й розширює буфер під довжину рядка, що усуває переповнення буфера фіксованого розміру (buffer overflow).
2. Версія з `getline` прочитає рядок у мільйон символів (за наявності пам'яті), тоді як фіксований `char buf[256]` через `fgets` читатиме рядок частинами по 255 символів, розбиваючи його на кілька «рядків» і ламаючи нумерацію/пошук.
3. Пам'ять звільняється автоматично в кінці області видимості (`scope`) змінної `content` за правилами володіння (RAII / `Drop`), рішення визначається на етапі компіляції правилами власності Rust.
4. Borrow checker не захищає від логічних помилок (наприклад, неправильна умова пошуку чи невірний код повернення), де немає порушення правил володіння та запозичень.
5. `cargo build` без змін не перекомпілює актуальні артефакти з кешу в `target/`. Схожість із `make` — у пропуску зайвої роботи для незмінених цілей; відмінність — `cargo` враховує метадані проєкту, залежності та параметри збірки, а не лише `mtime` файлів.
6. Якщо годинник системи збитий або файл змінено менш ніж за секунду / вручну підмінено мітку часу, `make` може пропустити перезбірку або перезбрати зайве.
7. `git merge` створює коміт злиття, зберігаючи паралельні гілки в графі, тоді як `git rebase` переносить послідовність комітів поверх цільової гілки, переписуючи їхні хеші[cite: 1]. Переписувати опубліковану історію небезпечно, бо це ламає історію в інших учасників, які вже спиралися на старі коміти.
8. Гілка — це лише файл із хешем коміту, тому її створення — це запис кількох десятків байтів незалежно від розміру проєкту[cite: 10].
9. `git bisect run` орієнтується на код виходу процесу (`0` — `good`, `1..127` крім `125` — `bad`), а не на текстовий вивід у `stdout`[cite: 2, 3, 4].
10. Пароль залишається в історії Git у попередніх об'єктах комітів, доки репозиторій не переписано й не очищено від старих об'єктів, а в публічному репозиторії вже міг бути скопійований.
11. Ні, не гарантує: логічно або семантично два фрагменти в одному файлі можуть суперечити один одному (наприклад, зміна назви функції в одному місці й виклик старого імені в іншому).
12. Без перевірки `NULL` розіменування вказівника при нестачі пам'яті призведе до невизначеної поведінки (часто — segmentation fault / падіння програми).

## 5. Висновки
Порівняння реалізацій `minigrep` на C та Rust показало компроміс між мінімалізмом і простотою інструментів C та жорсткими гарантіями безпеки пам'яті й сучасною екосистемою `cargo` у Rust. Робочий процес із гілками, вирішенням конфліктів, `rebase` та `git bisect` дозволяє безпечно інтегрувати зміни і швидко знаходити регресії в історії коду[cite: 1, 2, 3, 4].
