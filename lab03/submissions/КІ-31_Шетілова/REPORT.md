## 1. Гілка в Git як вказівник

Після `git switch -c lab03-shetilova` файл `.git/HEAD` містив рядок `ref: refs/heads/lab03-shetilova`, а файл `.git/refs/heads/lab03-shetilova` - хеш `2e67280981118239bc9cd449bca083209da980fd`.

`HEAD` не зберігає коміт, а лише вказує, яка гілка зараз поточна. Сама гілка - це маленький текстовий файл з одним хешем коміту, на який вона показує. Тому створення гілки майже безкоштовне: Git записує один новий файл, а не копіює проєкт. Новий коміт просто переписує хеш у файлі гілки, а `git switch` змінює рядок у `HEAD`. Це підтверджує тезу лекції, що гілка - вказівник.

## 2. Витік пам'яті в C

Щоб побачити витік, я тимчасово закоментувала `free(line)` і запустила `valgrind --leak-check=full ./minigrep test test.txt`. Ключові рядки виводу:

    in use at exit: 120 bytes in 1 blocks
    total heap usage: 4 allocs, 3 frees, 5,712 bytes allocated
    120 bytes in 1 blocks are definitely lost in loss record 1 of 1
       at 0x4850858: malloc (vg_replace_malloc.c:447)
       by 0x48FA7DC: getdelim (iogetdelim.c:65)
       by 0x4001369: main (minigrep.c:23)
    definitely lost: 120 bytes in 1 blocks

Valgrind показує, що з чотирьох виділень пам'яті звільнено лише три: буфер, який `getline` (всередині вона викликає `getdelim`) виділила для рядка в `main` на 23-му рядку, не звільнено перед завершенням. Через один блок у 120 байтів і стоїть «definitely lost»: на нього не лишилося жодного вказівника. Витік не заважає видати правильну відповідь, тому без інструмента його не видно. Після повернення `free(line)` після циклу звіт чистий.

## 3. Чому make не перезбирає без потреби

Перший `make` зібрав програму. Другий виклик без змін відповів `make: Nothing to be done for 'all'`. Після `touch minigrep.c` `make` зібрав її знову.

`make` порівнює час останньої зміни цілі (`minigrep`) і залежності (`minigrep.c`), який бере з метаданих файлової системи. Якщо ціль новіша за залежність, перезбирати нічого. `touch` оновлює час `minigrep.c`, тому вихідний файл стає новішим за бінарник, і `make` повторює команду компіляції.

## 4. Безпека пам'яті в Rust

Щоб перевірити, чи Rust пропустить посилання на локальну змінну, я додала функцію без параметрів:

    fn bad() -> &String {
        let s = String::from("x");
        &s
    }

Компілятор повернув помилку:

    error[E0106]: missing lifetime specifier
      --> src/main.rs:41:13
       |
    41 | fn bad() -> &String {
       |             ^ expected named lifetime parameter
       |
       = help: this function's return type contains a borrowed value, but there is no value for it to be borrowed from

`E0106` означає, що для посилання в типі результату не вказано параметр часу життя: компілятор не може вивести, від чого воно залежить, бо функція не має вхідних посилань. Це лише симптом. Щоб побачити сам дефект, я дала функції параметр (`fn bad(_x: &str) -> &String`), з яким час життя виводиться, і отримала:

    error[E0515]: cannot return reference to local variable `s`
      --> src/main.rs:43:5
       |
    43 |     &s
       |     ^^ returns a reference to data owned by the current function

Ця помилка ловить саме дефект із лекції: висячий вказівник. `s` належить функції і знищується на її виході, тому посилання `&s` після повернення вказувало б на звільнену пам'ять. У C такий `return &локальна_змінна` компілюється (щонайбільше з попередженням), а при використанні дає невизначену поведінку. Rust перевіряє час життя посилань під час компіляції, тому цей дефект не доходить до запуску. Після експерименту я прибрала `bad()` і повернула `src/main.rs`.

## 5. Порівняння C та Rust

| Показник | C | Rust |
| --- | --: | --: |
| Рядків коду (`wc -l`) | 35 | 39 |
| Перша чиста збірка | 0,442 с | 0,958 с |
| Повторна збірка без змін | 0,007 с | 0,039 с |
| Бінарник, debug | 19 584 Б (19,1 КіБ) | 4 798 032 Б (4,6 МіБ) |
| Бінарник, release (`-O2` / `--release`) | 16 400 Б (16,0 КіБ) | 460 200 Б (449 КіБ) |

Rust-програма довша на 4 рядки, бо обробка помилки читання файла записана через `match`, а лічильник рядків дає `enumerate()`. Rust збирається довше: перша збірка вдвічі довша, бо `cargo` запускає `rustc`, який аналізує час життя посилань і оптимізує узагальнений код, а `gcc` компілює один невеликий файл. Повторна збірка без змін у обох інструментів майже миттєва, бо вони нічого не перекомпільовують: `make` порівнює час зміни файлів, а `cargo` перевіряє відбитки джерел. Через додаткові перевірки `cargo` витрачає на це 0,039 с проти 0,007 с.

### Чому debug-бінарник Rust такий великий (4,6 МіБ)

Розмір складається з трьох причин, і я перевірила їх вимірами.

1. Налагоджувальна інформація (DWARF) займає майже весь файл. Я видалила її командою `strip --strip-debug` з копії debug-бінарника: розмір впав з 4 798 032 до 514 472 байтів. Отже, налагоджувальна інформація важить 4 283 560 байтів, тобто близько 4,1 МіБ, або 89 % файла. Debug-збірка Rust зберігає її для всієї стандартної бібліотеки, а не тільки для моїх 39 рядків; у C-програмі налагоджувальна інформація описує лише мій невеликий файл.
2. Стандартна бібліотека Rust вбудована в бінарник. Навіть без налагоджувальної інформації Rust-бінарник має 502 КіБ проти 19 КіБ у C. `ldd` показує, що обидві програми динамічно підключають системну `libc.so.6` (Rust додатково `libgcc_s.so.1` для розкручування стека), тобто різниця не в libc. Це код самого `std`, який компілюється в бінарник: форматування (`println!`, `eprintln!`), робота з файлами, обробка паніки, збір аргументів. У C усе це лежить у спільній бібліотеці `libc`, яку програма лише підключає.
3. Debug-режим не оптимізує код: `cargo build` без `--release` не вилучає зайвого й не вбудовує функції, тож лишається більше машинного коду, ніж потрібно.

### Чи зберігається різниця в release

Так, але вона значно менша. У release Rust зменшується з 4,6 МіБ до 449 КіБ (в 10 разів): оптимізація прибирає зайвий код, а налагоджувальної інформації за замовчуванням немає. Проте бінарник усе одно в 28 разів більший за C-версію (460 200 проти 16 400 байтів), бо вбудований `std` лишається. Для C різниця між debug (19 584 Б) і `-O2` (16 400 Б) мізерна, бо в простій програмі нічого оптимізувати й налагоджувальної інформації мало.


## 6. Конфлікт злиття та синхронізація

Щоб отримати конфлікт, я від робочої гілки створила дві гілки: `conflict-demo-a` і `conflict-demo-b`. У кожній я дописала в кінець `REPORT.md` рядок «Висновок: …», але різний: у A - «Rust виграє за безпекою.», у Б - «C виграє за простотою інструментів.». Команда `git merge conflict-demo-a` у гілці Б зупинилася з повідомленням `CONFLICT (content): Merge conflict in ... REPORT.md`, а `git status` показав стан `both modified`. У файлі Git залишив маркери:

    <<<<<<< HEAD
    Висновок: C виграє за простотою інструментів.
    =======
    Висновок: Rust виграє за безпекою.
    >>>>>>> conflict-demo-a

Верхня частина (до `=======`) - це версія гілки, у якій я стояла (`conflict-demo-b`), нижня - та, що вливається. Я написала один справжній висновок, який поєднує обидва варіанти, прибрала всі три маркери, виконала `git add REPORT.md` і `git commit`; Git запропонував повідомлення `Merge branch 'conflict-demo-a' into conflict-demo-b`. Потім у робочій гілці я виконала `git merge conflict-demo-b` (проста перемотка, без нового коміту) і видалила допоміжні гілки.

Граф історії після злиття:

    *   00d558a (HEAD -> lab03-shetilova) Merge branch 'conflict-demo-a' into conflict-demo-b
    |\
    | * 7a94f06 варіант A висновку
    * | e903a74 варіант Б висновку
    |/
    * eefb6f6 ЛР3: реалізація minigrep мовою Rust
    * 85da855 ЛР3: реалізація minigrep мовою C
    * ec177bc ЛР3: каркас каталогу роботи

Коміт злиття `00d558a` має двох батьків: у виводі `git cat-file -p HEAD` видно два рядки `parent` - `e903a74` (варіант Б) і `7a94f06` (варіант A). Звичайний коміт має одного батька; саме коміт злиття з'єднує дві гілки історії.

Git не міг вирішити конфлікт сам, бо обидві гілки змінили те саме місце файла по-різному відносно спільного предка, а обидва рядки синтаксично коректні: це звичайний текст. Git порівнює лише текст, а не зміст, тому не має способу дізнатися, який висновок правильний. Вибір між двома однаково допустимими варіантами може зробити тільки людина.

Синхронізація з репозиторієм курсу: `git fetch upstream` і перевірка `git log --oneline HEAD..upstream/main` показали, що нових комітів курсу немає (вивід порожній): моя гілка вже стоїть на актуальному `upstream/main` (`2e67280`), тож переносити нічого не потрібно. Звичайний `git rebase upstream/main` у моїй гілці все ж спробував відтворити коміти заново, відкинув коміт злиття й знову зупинився на тому самому конфлікті в `REPORT.md` (варіанти A і Б); я скасувала його командою `git rebase --abort`. Це показує, що rebase переписує історію і за замовчуванням не зберігає коміти злиття (для цього існує ключ `--rebase-merges`); тому rebase виконують у власній гілці до створення злиттів, а коли синхронізація не потрібна, його не запускають.

## 7. Пошук зламаного коміту через git bisect

Навчальну історію створив скрипт `make-bisect-repo.sh`: 30 комітів, поточний стан зламаний (`./test.sh` повертає код 1). Для ручного пошуку я виконала `git bisect start`, позначила поточний стан як зламаний (`git bisect bad`), а перший коміт історії як справний (`git bisect good $(git rev-list --max-parents=0 HEAD)`), після чого після кожної перевірки запускала `./test.sh && git bisect good || git bisect bad`. Git щоразу перемикав мене на коміт посередині діапазону і повідомляв, скільки комітів лишилося перевірити: 14, 7, 3, 0, 0. Всього знадобилося 5 перевірок (коміти «прибрано зайвий пробіл (15)», «уточнено коментар до циклу (22)», «додано приклад використання (18)», «форматування за стилем проєкту (17)» і «оптимізовано цикл підсумовування»).

Автоматичний пошук: `git bisect start HEAD $(git rev-list --max-parents=0 HEAD)` і `git bisect run ./test.sh`. Git сам запустив скрипт 5 разів і дійшов до того самого коміту.

Двійковий пошук щоразу відкидає половину діапазону, тому очікувана кількість кроків становить приблизно log2 N, де N - кількість комітів: log2 30 = 4,9, тобто 5. Отримані 5 перевірок збігаються з цією оцінкою (у лінійному пошуку їх було б до 30).

Перший зламаний коміт:

    d22571345e4f092fc15eec24c0005e6b303e8838
    оптимізовано цикл підсумовування

Він змінив один рядок у `sum.c`:

    -    for (int i = 1; i < argc; i++) {
    +    for (int i = 1; i <= argc; i++) {

Помилка «на одиницю»: через `<=` цикл виконує зайву ітерацію з `i == argc`, а елемент `argv[argc]` дорівнює `NULL`, тому `atol(argv[i])` викликається від нульового вказівника - це невизначена поведінка, і тест перестає проходити. Повідомлення коміту («оптимізовано») не відповідає змісту: це не оптимізація, а помилка, і саме такі розбіжності ускладнюють пошук без `bisect`.

## 8. Атомарні коміти та git bisect

Якщо один коміт містить тиждень роботи над п'ятьма різними задачами, `git bisect` усе одно знайде «перший поганий коміт», але цей коміт буде величезним, і з нього не видно, яка саме з п'яти змін зламала програму. Мені довелося б розбирати його вручну і шукати винну частину, тобто двійковий пошук лише переносить задачу всередину одного коміту. Крім того, такий коміт неможливо скасувати частково: `git revert` забрав би всі п'ять задач разом, включно з робочими.

Тому вимога атомарних комітів (один коміт - одна логічна зміна з поясненням «навіщо») прямо пов'язана з `bisect`: що менший і цілісніший коміт, то точніше `bisect` вказує причину помилки. У моєму навчальному прикладі знайдений коміт змінив один рядок у `sum.c`, і причину було видно одразу.

## 9. Контрольні питання

### 1. Чому `getline` сама виділяє буфер

Програма не знає наперед, наскільки довгим буде рядок. `getline` виділяє буфер і збільшує його за потреби, тому не доводиться вгадувати розмір масиву. Це прибирає клас помилок переповнення буфера: запис за межі масиву, коли рядок довший за передбачений розмір (і втрату хвоста рядка, якщо його просто обрізати).

### 2. Рядок у мільйон символів

C-версія з `getline` прочитає такий рядок повністю: буфер зросте до потрібного розміру, якщо вистачить пам'яті. Версія з `char buf[256]` і `fgets` читала б рядок шматками по 255 символів: програма сприйняла б один рядок як кілька тисяч, зіпсувала б нумерацію і могла б пропустити шаблон, що потрапив на межу двох шматків. Переповнення при цьому немає, бо `fgets` обмежує читання розміром буфера.

### 3. Коли Rust звільняє пам'ять без `free`

Рядок `content` володіє пам'яттю з вмістом файла. Коли змінна виходить з області видимості (у моєму випадку наприкінці `main`), для неї викликається `Drop`, і пам'ять звільняється. Рішення ухвалює компілятор: він за правилами володіння під час компіляції вставляє виклик у потрібне місце, збирача сміття немає.

### 4. Помилка, від якої Rust не захищає

Наприклад, логічна помилка: умова `<=` замість `<` у циклі (як у навчальному прикладі з `bisect`) або пошук за неправильною умовою. Також Rust не забороняє витоку пам'яті, наприклад, через цикл із `Rc`. Перевіряльник запозичень перевіряє лише, хто володіє даними і чи не пережили посилання свої дані; що програміст мав на увазі, він не знає.

### 5. Чому `cargo build` без змін миттєвий

`cargo` зберігає в `target/` відбитки джерел і параметрів збірки; якщо нічого не змінилося, `rustc` не запускається. Це схоже на `make`: обидва пропускають роботу, яка вже зроблена. Різниця в тому, що `make` порівнює час зміни файлів за правилами, які я вписала в `Makefile` вручну, а `cargo` сам знає граф залежностей з `Cargo.toml` і модулів і враховує також версію компілятора, прапорці та версії залежностей.

### 6. Коли порівняння часу в `make` помиляється

Коли час файла не відображає зміни: системний годинник вказує неправильний час, файли відновлено з архіву чи скопійовано зі збереженням старого часу (`cp -p`, `rsync -t`), і вихідний файл здається старішим за бінарник, хоча його вміст новіший. Хибний результат також виникає, якщо залежність не вказана в `Makefile` (наприклад, заголовочний файл): його зміна не викликає перезбірки, і бінарник залишається старим.

### 7. `merge` і `rebase`

`merge` зберігає обидві лінії історії й створює коміт злиття з двома батьками, тому граф розгалужується. `rebase` бере мої коміти й відтворює їх заново поверх іншої гілки, тому історія лінійна, але коміти отримують нові хеші. Переписувати опубліковану історію небезпечно: інші люди могли вже спертися на старі коміти, і після зміни хешів їхні гілки розійдуться з вашими (потрібен примусовий `push`, виникають дублі й конфлікти).

### 8. Чому гілка створюється миттєво

Гілка - це не копія проєкту, а маленький файл `.git/refs/heads/<назва>` з одним хешем коміту. Створення гілки це запис одного такого файла; коміти й файли вже лежать у сховищі й нікуди не копіюються, тому розмір проєкту не має значення.

### 9. Чому `bisect run` потребує коду завершення

Git запускає скрипт як окремий процес і з'ясовує результат лише за кодом завершення: 0 означає «справний», будь-яке ненульове значення (крім 125, «пропустити») - «зламаний». Надрукований текст «працює»/«не працює» Git не вміє інтерпретувати, а код завершення - універсальний спосіб, яким програма повідомляє результат для автоматизації.

### 10. Пароль у коміті

Наступний коміт лише додає нову версію файла, а попередня разом з паролем лишається в історії: її можна побачити через `git log -p` чи `git show`. Якщо коміт уже надіслано в `origin`, хтось міг його клонувати. Тому такий пароль вважають скомпрометованим і змінюють; очищення історії допомагає лише для нових клонів.

### 11. Злиття без конфлікту

Не гарантує. Git порівнює текст, а не зміст. Контрприклад: один студент перейменував функцію `parse()` на `parse_line()` у її визначенні, а інший у тій самій гілці історії додав в іншому місці виклик `parse(...)`. Рядки різні, Git зливає їх без конфлікту, але в результаті виклик посилається на неіснуючу функцію, і програма не збирається.

### 12. `malloc` без перевірки на `NULL`

За нестачі пам'яті `malloc` повертає `NULL`. Якщо звернутися за таким вказівником, виникає невизначена поведінка, на практиці аварійне завершення з помилкою сегментації, часто без пояснення причини й зі втратою даних. Правильно перевірити результат, вивести повідомлення (`perror`) і завершитися з ненульовим кодом.

## 10. Висновок

У цій роботі я реалізувала одну утиліту, `minigrep`, мовами C і Rust, і вони дали однаковий вивід і однакові коди повернення (0, 1, 2). Витік пам'яті в C я побачила через Valgrind (120 байтів у 1 блоці після прибирання `free`), а Rust відхилив небезпечне посилання на локальну змінну ще під час компіляції. Rust збирається повільніше, а його debug-бінарник у 245 разів більший за C-версію, головно через налагоджувальну інформацію (близько 89 % файла) і вбудовану стандартну бібліотеку; у release різниця зменшується, але лишається (460 200 проти 16 400 байтів). Для невеликої утиліти зручнішим виявився C завдяки простій збірці, а Rust надійніший: помилки роботи з пам'яттю він ловить заздалегідь.

У Git я перевірила, що гілка - це файл з хешем коміту, навмисно створила й розв'язала конфлікт злиття (коміт злиття має двох батьків) і побачила, що звичайний `rebase` не зберігає коміти злиття. Через `git bisect` я знайшла зламаний коміт у 30-комітній історії за 5 перевірок, що збігається з log2 30; причиною виявилася помилка «на одиницю» (`<=` замість `<`) у циклі.
